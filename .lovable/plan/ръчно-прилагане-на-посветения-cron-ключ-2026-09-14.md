# Ръчно прилагане на посветения cron ключ

## Цел
Потребителят изпълнява еднократно подготвената SQL миграция, защото платформата не позволява на агента да създава Vault secrets. След това агентът активира cron задачите 7–10 и проверява шестте cron функции.

## Стъпки за изпълнение

1. **Отворете SQL редактора**
   - В Lovable Cloud отидете в секцията за SQL редактор (More → Backend → SQL editor).

2. **Заредете файла с миграцията**
   - В проекта отворете `docs/migrations/20260912213000_internal_operational_cron_secret.sql`.
   - Копирайте **целия** текст (173 реда).

3. **Изпълнете текста в SQL редактора**
   - Поставете го в редактора и натиснете Run.
   - Текстът е идемпотентен — ако вече е изпълнен, повторното пускане няма да промени нищо.
   - Стойността на ключа се генерира директно от PostgreSQL (256 бита) и не се показва никъде.

4. **Проверете резултата**
   - Уверете се, че изпълнението завършва без грешка.
   - Не е нужно да копирате или записвате стойността на ключа — той живее само в PostgreSQL Vault.

5. **Съобщете ми**
   - Щом миграцията мине успешно, пишете „Готово" или пратете screenshot с успешния резултат.
   - След това аз активирам задачите 7–10 и проверявам всяка от шестте cron функции с положителен dry-run тест.

## Какво прави миграцията
- Създава функция `public.verify_internal_cron_secret(_candidate text)`, която проверява 64-символен hex ключ през PostgreSQL Vault.
- Създава 256-битов Vault secret с име `internal_operational_cron_secret_v1`.
- Пренасочва четирите cron задачи (7–10) от стария идентификатор `email_queue_service_role_key` към новия `internal_operational_cron_secret_v1`.
- Оставя задачите паузирани (`active = false`) — активирането е отделна стъпка.

## Извън обхвата на този план
- Без промени в цени, плащания, feature flags, frontend, Edge функции или публикуване.
- Без създаване на secrets от страна на агента.
